# Production-repository practices in four reference repos

Audited 2026-07-23 from the public repositories at these commits:

- `pingdotgg/t3code` — [`b41e89e`](https://github.com/pingdotgg/t3code/tree/b41e89eba9cd232cc3257b400fc30972a9b53438)
- `livekit/agents-js` — [`871ca12`](https://github.com/livekit/agents-js/tree/871ca12c28aa061328e3a89629cf1baa7493a7d6)
- `openai/codex` — [`808d3c2`](https://github.com/openai/codex/tree/808d3c2702ce8eae007c457aa930e7c3b68dd5f6)
- `mattpocock/skills` — [`ed37663`](https://github.com/mattpocock/skills/tree/ed37663cc5fbef691ddfecd080dff42f7e7e350d)

“Confirmed” below means the behavior is encoded or documented in the repository at that commit. “Inference” is used where the public files support a conclusion but do not prove private GitHub settings or external infrastructure. This audit does not treat an installable library or skill bundle as an application deployment.

## Executive comparison

| Repository | What it ships | Strongest practice to borrow | Important limit |
| --- | --- | --- | --- |
| `pingdotgg/t3code` | CLI, desktop/mobile/web apps, and a hosted relay | One release pipeline validates, packages, publishes, and deploys channel-specific artifacts | It is an early product with a large multi-app topology; its workflow complexity is not a sensible starting point |
| `livekit/agents-js` | Public Node.js framework plus many npm plugins | Small, conventional library pipeline: build/lint/typecheck/test, Changesets, trusted npm publishing, automated dependency updates | It publishes libraries and docs; it does not deploy the applications built with the framework |
| `openai/codex` | Cross-platform CLI plus SDKs and supporting binaries | Version-controlled required-check aggregator, fast PR CI versus full post-merge CI, pinned Actions, signed multi-platform releases | This is a very large Rust/SDK workspace; reproducing its matrix early would be ceremony without equivalent risk |
| `mattpocock/skills` | Markdown-based agent skills and a Claude Code plugin manifest | Explicit domain language, repository invariants, composable workflow documentation, lightweight Changesets release tags | It has no checked-in validation/test CI at the audited commit; it is a process-content repo, not an app-production model |

## `pingdotgg/t3code`

- **Product and repository type — confirmed.** T3 Code describes itself as a web GUI for coding agents and distributes an npm CLI plus desktop packages; its workspace contains `apps/*`, `infra/*`, packages, and scripts. It is therefore a multi-surface application monorepo, not merely a reusable package. - **Languages and contributor setup — confirmed.** The root is a TypeScript/Node workspace using Vite+, pnpm, and a pinned Node/package-manager contract (`node ^24.13.1`, `pnpm 11.10.0`). Contributors install `vp` and then run `vp i`. [package scripts and engines](https://github.com/pingdotgg/t3code/blob/b41e89eba9cd232cc3257b400fc30972a9b53438/package.json#L1-L59) · [setup](https://github.com/pingdotgg/t3code/blob/b41e89eba9cd232cc3257b400fc30972a9b53438/README.md#L64-L90)

The same release pipeline runs check, typecheck, and test again before publishing. [CI triggers and jobs](https://github.com/pingdotgg/t3code/blob/b41e89eba9cd232cc3257b400fc30972a9b53438/.github/workflows/ci.yml#L1-L101) · [release preflight](https://github.com/pingdotgg/t3code/blob/b41e89eba9cd232cc3257b400fc30972a9b53438/.github/workflows/release.yml#L152-L167)
- **Tests — confirmed.** Tests are a first-class root command, while the relay documentation asks backend changes to include tests against business logic with external dependencies represented at their boundary. [root commands](https://github.com/pingdotgg/t3code/blob/b41e89eba9cd232cc3257b400fc30972a9b53438/package.json#L19-L30) · [relay test guidance](https://github.com/pingdotgg/t3code/blob/b41e89eba9cd232cc3257b400fc30972a9b53438/infra/relay/README.md#L56-L75)
- **Dependencies and security automation — confirmed with a gap.** pnpm explicitly controls which dependencies may execute install/build scripts and centralizes versions in a catalog. At this commit, the checked-in `.github` tree contains no Dependabot configuration and the repository has no Renovate configuration; Actions are referenced by movable major-version tags rather than immutable SHAs. [pnpm controls](https://github.com/pingdotgg/t3code/blob/b41e89eba9cd232cc3257b400fc30972a9b53438/pnpm-workspace.yaml#L8-L52) · [workflow tree](https://github.com/pingdotgg/t3code/tree/b41e89eba9cd232cc3257b400fc30972a9b53438/.github/workflows) · [example Action references](https://github.com/pingdotgg/t3code/blob/b41e89eba9cd232cc3257b400fc30972a9b53438/.github/workflows/ci.yml#L14-L23)
- **Release and publication — confirmed.** Stable semver tags, scheduled three-hour nightlies, and manual stable/nightly releases share a preflight; the pipeline builds desktop artifacts, publishes the CLI to npm, creates a GitHub Release with generated notes, and uses stable/nightly channels. [release triggers and version rules](https://github.com/pingdotgg/t3code/blob/b41e89eba9cd232cc3257b400fc30972a9b53438/.github/workflows/release.yml#L1-L159) · [npm and GitHub publication](https://github.com/pingdotgg/t3code/blob/b41e89eba9cd232cc3257b400fc30972a9b53438/.github/workflows/release.yml#L608-L780)
- **Application deployment — confirmed.** The hosted web app deploys to Vercel only after release publication and aliases stable/nightly domains. Separately, every push to `main` deploys the production relay through Alchemy to Cloudflare-backed infrastructure under a GitHub `production` environment; pull requests do not deploy relay stages. Mobile preview deployment is label-gated on PRs, while production EAS builds/OTA updates are manual workflow dispatches. [web deploy](https://github.com/pingdotgg/t3code/blob/b41e89eba9cd232cc3257b400fc30972a9b53438/.github/workflows/release.yml#L782-L893) · [relay workflow](https://github.com/pingdotgg/t3code/blob/b41e89eba9cd232cc3257b400fc30972a9b53438/.github/workflows/deploy-relay.yml#L1-L80) · [relay deployment contract](https://github.com/pingdotgg/t3code/blob/b41e89eba9cd232cc3257b400fc30972a9b53438/infra/relay/README.md#L77-L121) · [mobile preview](https://github.com/pingdotgg/t3code/blob/b41e89eba9cd232cc3257b400fc30972a9b53438/.github/workflows/mobile-eas-preview.yml#L1-L22) · [mobile production](https://github.com/pingdotgg/t3code/blob/b41e89eba9cd232cc3257b400fc30972a9b53438/.github/workflows/mobile-eas-production.yml#L1-L35)

## `livekit/agents-js`

- **Product and repository type — confirmed.** This is the Node.js distribution of LiveKit’s server-side realtime agent framework, with a core npm library, provider plugins, and examples. It is framework/tooling source, not a deployed end-user application. [README](https://github.com/livekit/agents-js/blob/871ca12c28aa061328e3a89629cf1baa7493a7d6/README.md#L20-L58) · [workspace](https://github.com/livekit/agents-js/blob/871ca12c28aa061328e3a89629cf1baa7493a7d6/pnpm-workspace.yaml#L1-L4)

Contributors are told to branch from `main`, format/lint locally, add SPDX headers, document public API, and sign a CLA. [root scripts](https://github.com/livekit/agents-js/blob/871ca12c28aa061328e3a89629cf1baa7493a7d6/package.json#L1-L59) · [contributor contract](https://github.com/livekit/agents-js/blob/871ca12c28aa061328e3a89629cf1baa7493a7d6/CONTRIBUTING.md#L7-L53)

Actions are pinned to full commit SHAs. [build workflow](https://github.com/livekit/agents-js/blob/871ca12c28aa061328e3a89629cf1baa7493a7d6/.github/workflows/build.yml#L1-L62)

## What the evidence suggests for a new production app

These are inferences from the confirmed practices above, not claims about the reference repositories:

1. **Start with the LiveKit-shaped baseline:** one deterministic install, one root `check` command, PR + `main` CI, format/lint/typecheck/build/tests, pinned Actions, Renovate/Dependabot, and Changesets only if the product actually publishes packages.
2. **Borrow T3 Code’s separation of release from deployment:** validate once, produce immutable versioned artifacts, then deploy the exact artifact through an explicit production environment. Keep preview and production paths visibly distinct.
3. **Borrow Codex’s required-check aggregator and fast/full split only when scale earns it:** one stable branch-protection check avoids ruleset churn; fast PR checks protect review latency while exhaustive matrices can run post-merge or before release.
4. **Borrow Matt Pocock’s domain and agent instructions, but enforce invariants in CI:** prose explains ownership and intent; a machine check prevents drift.
5. **Do not confuse popularity with completeness:** the audited repos contain deliberate tradeoffs and visible gaps. Adopt controls because they cover this product’s risks, not because a reference repo has them.
